# xrCore: Типы и математика

Базовые типы, векторы, матрицы, кватернионы, геометрические примитивы, FPU/CPU.

## Почему в движке свои типы

**`u8`/`u32`/`f32`** нужны для переносимости. `int` в C++ не обязан быть 32-битным на любой платформе, `long` — 64-битным и т.д. Код, который пишет `u32`, гарантированно работает одинаково на любой платформе и в любом компиляторе — и при этом сразу видно, что тут целое 32 бита, а не «какое-то число». Плюс `xrCore` должен работать и на MSVC, и на Borland, где набор встроенных типов разный — `_types.h` это унифицирует.

**`Fvector`/`Fmatrix`/`Fquaternion`** — потому что движку нужна не «стандартная математика», а **оптимизированная**: у этих структур переопределены все операции (`+`, `-`, `*`, `dot`, `cross`), они могут быть ускорены SIMD (SSE/AVX) и работают с row-major layout, который ожидает DirectX. `std::`-математики просто не существует, а «ручные» `float[4]` без методов сделают код ненаписываемым. Поэтому `Fvector pos; pos.add(dir, 1.f)` — а не `pos[0]+=dir[0]; ...`.

## Векторы — `_vector3d.h`, `_vector2.h`, `_vector4.h`

### `Fvector` (alias `_vector3<float>`)

```cpp
struct Fvector {
    float x, y, z;
    // operator[], set, add, sub, mul, div, ...
};
```

- **Row-column order**: `x`, `y`, `z` — компоненты.
- **Доступ**: `v.x`, `v.y`, `v.z`, или `v[0]`, `v[1]`, `v[2]`.
- **Операции**: `set`, `add`, `sub`, `mul`, `div`, `dot`, `cross`, `length`, `square_length`, `normalize`, `lerp`, `slerp`, `angle`, `reflect`, `project`, `intersect`, ...
- **Возврат `Self&`**: все мутации возвращают `*this` (chainable).

### Как это выглядит в коде

Типичные паттерны из движка:

```cpp
// src/xrGame/cameralook.cpp — позиция камеры смещается на точку:
Fvector vPosition;
vPosition.add(point);              // vPosition = vPosition + point

// src/xrGame/poses_blending.cpp — лерп между двумя позициями позы:
p.c.lerp(p0, p1, factor);         // p.c = lerp(p0, p1, factor)

// сдвиг с масштабом: mul — покомпонентно, add — «в-place»
v.mul(0.5f);          // v = v * 0.5  (компоненты v.x,v.y,v.z *= 0.5)
v.add(dir);           // v = v + dir
```

- `v.add(point)` — это `v = v + point` (in-place). **Важно**: `add` **не** имеет формы «вектор + множитель». Перегрузы `add(a, v)` и `add(a, s)` — это **смешивание двух** векторов/скаляра: `this = a + v` / `this = a + s` (текущее значение стирается). Если нужен сдвиг с масштабом — сначала `mul(s)`, потом `add(v)`.
- `v.mul(0.5f)` — **покомпонентно**: каждая компонента умножается на `0.5f`. Это не `dot`.
- `lerp(a, b, t)` — **заменяет** текущее значение: `this = a + (b-a)*t`, а не «добавляет» к текущему. Путать с `add` — частая ошибка.
- `v.normalize()` — на месте: `v = v / |v|`.

### `Fvector2`, `Fvector4`

Аналогично, 2 и 4 компоненты.

### `Ivector3`, `Ivector4`, `Ivector2`

Целочисленные версии (`s32`).

## Матрицы — `_matrix.h`, `_matrix33.h`

### `Fmatrix` (alias `_matrix<float>`)

**DirectX-compliant, row-column order**:

```
m11 m12 m13 m14  ← первая строка
m21 m22 m23 m24
m31 m32 m33 m34
m41 m42 m43 m44  ← трансляция (m41, m42, m43)
```

**Хранение**: `m[4][4]` или union:

- `_11.._44` — поэлементно
- `i, j, k, c` — строки как `Fvector` (R, N, D, T)
- `m[4][4]` — массив

**Множение**: `[x'y'z'1] = [xyz1][M]`, т.е. **вектор-строка × матрица**.

#### Почему трансляция в `m41, m42, m43`, а не в `m14, m24, m34`

Это самое частое место ошибки. Причина — **конвенция вектора-строки**. Матрица применяется как `[x' y' z' 1] = [x y z 1] × M`, то есть точка — **строка**, умноженная на матрицу справа. Раскройте это умножение для x':

```
x' = x*m11 + y*m21 + z*m31 + 1*m41
```

Четвёртая компонента гомогенного вектора — это `1`, и она умножается на **четвёртый столбец** матрицы (`m14, m24, m34, m44` по столбцам, т.е. элементы `m14 m24 m34 m44` — это последняя **строка** памяти, но при умножении «вектор-строка × матрица» вклад «+1 × что-то» берётся из **первого элемента каждого столбца**: `m11, m21, m31, m41`). Значит трансляция по X живёт в `m41` (она складывается с x' как `1*m41`), по Y — в `m42`, по Z — в `m43`. Это не произвольный выбор: это следствие того, что вектор — строка.

Если бы вектор был **столбцом** (`M × [x y z 1]ᵀ`), трансляция легла бы в `m14, m24, m34` (последний столбец). Так делают OpenGL/стандартная линейная алгебра. DirectX — и этот движок — выбрали обратное, и вся документация/код это учитывает.

> **Запомнить на пальцах**: строка-вектор × матрица → трансляция в **последней строке памяти** (`m41 m42 m43`), а не в последнем столбце. Матрица перемещения на 5 по X:
>
> ```cpp
> Fmatrix M; M.identity(); M._41 = 5.f;   // ← а НЕ M._14
> // теперь M * точка сдвинет её на (5, 0, 0)
> ```

**Пример: поворот вокруг оси Y на 90°**

Положительный угол = по часовой (DirectX convention). Поворот вокруг Y смешивает **только** компоненты `x` и `z`; строки 1 и 3 заполняются из `cos(t)`/`sin(t)`, трансляция не трогается (поворот вокруг начала координат). Конкретная расстановка знаков — смотрите в `Fmatrix::rotation` / `mk_xform` в `_matrix.h` (там она зафиксирована и проверена), а не выводите руками: знак зависит от ориентации оси и конвенции «по часовой», и именно здесь новички чаще всего ошибаются.

Главное, что нужно удержать при ручной сборке любой матрицы: **трансляция живёт в `m41..m43`** (последняя строка памяти), а не в `m14..m34`.

**Примечания**:

- Положительный угол = **по часовой** (DirectX convention).
- `mul(A, B)` = трансформация B, затем A.
- Последовательность поворота: **ZXY**.
- `I, J, K, C` = `R, N, D, T` (Right, Normal, Direction, Translation).

**Ключевые методы**: `set`, `add`, `sub`, `mul`, `inverse`, `transpose`, `det`, `rotation`, `translation`, `lerp`, `slerp`, `axis_angle`, `euler_angles`, `look_at`, ...

### `Fmatrix33` (alias `_matrix33<float>`)

3×3, только ротация (без трансляции).

## Кватернионы — `_quaternion.h`

### `Fquaternion` (alias `_quaternion<float>`)

**Формат**: `(s, v)` где `s = w` (скаляр), `v = [x, y, z]` (вектор).

```
q = w + xi + yj + zk
q = (s, v) = [s, (x, y, z)]
```

**Свойства**:

- `||q||` = `sqrt(w² + x² + y² + z²)`; unit quaternion: `||q|| == 1`.
- `q'` (конъюгат) = `(w, -v)`.
- `qinverse` = `q' / (q·q')`; для unit: `qinverse == q'`.
- **Не коммутативны**: `q1*q2 != q2*q1`.
- **Ассоциативны**: `(q1*q2)*q3 == q1*(q2*q3)`.

**Ротация**: угол `t` вокруг единичного вектора `u`:

```
s = cos(t/2)
v = u * sin(t/2)
```

**Применение к точке** `p = (px, py, pz)`, `P = (0, p)`:

```
p_rotated = q * P * qinverse   (= q * P * q' для unit)
```

**Сложение раций** `q1`, затем `q2`: `qc = q2 * q1`.

**Интерполяция**:

- Линейная (lerp) — не гарантирует unit.
- **Slerp** (сферическая): `q(t) = q1 * sin((1-t)w)/sin(w) + q2 * sin(t*w)/sin(w)`, где `w = arccos(q1·q2)`.

**Множение**:

```
q1 = (s1, v1), q2 = (s2, v2)
q1*q2 = (s1*s2 - dot(v1,v2),  s1*v2 + s2*v1 + cross(v1,v2))
```

### Когда использовать кватернион вместо матрицы

Коротко: **когда нужна интерполяция поворотов**.

- Матрицу поворота нельзя просто «проинтерполировать» (lerp между двумя матрицами даёт не-ортонобельную матрицу — поворот + искажение). Кватернион — сфера, по которой можно идти **сферически** (`slerp`) и получать в каждой точке **корректный unit-поворот**.
- У кватерниона нет **gimbal lock** (заклинивание оси) — проблемы, которая у euler-углов появляется при наклоне ~90°.
- Меньше ошибок накопления: unit-кватернион нормализуется одной операцией, а у матрицы ортонормальность «уплывает» медленнее, но её восстановление дороже.

Поэтому в движке повороты хранятся/интерполируются в кватернионах, а в «рабочую» форму (для рендера/физики) переводятся в матрицы одним вызовом.

**Пример из движка** — `src/xrGame/poses_blending.cpp` (смешивание поз анимации):

```cpp
poses_interpolation::poses_interpolation(const Fmatrix& m0, const Fmatrix& m1):
    p0(m0.c), p1(m1.c),
    q0(Fquaternion().set(m0)), q1(Fquaternion().set(m1))   // матрицы → кватернионы
{}

void poses_interpolation::pose(Fmatrix& p, float factor) const
{
    p.rotation(Fquaternion().slerp(q0, q1, factor));   // поворот — slerp по кватернионам
    p.c.lerp(p0, p1, factor);                           // позиция — обычный lerp
}
```

И в камере — `src/xrGame/cameralook.cpp:295`:

```cpp
new_dir.slerp(m_current_dir, m_final_dir, Device.fTimeDelta); // плавное «докручивание» взгляда
m_current_dir.set(new_dir);
Fmatrix rm; rm.rotation(m_current_dir);                       // кватернион → матрица
```

Позиция (`c`) интерполируется обычным `lerp` — она вектор, а не поворот. Поворот — `slerp` по кватернионам, потом в матрицу.

## CPU — `_math.h`, `cpuid.h`

### `_processor_info`

Заполняется `CPUID`-инструкцией при старте:

- ВENDOR, Family, Model, Stepping
- Флаги: SSE, SSSE3, SSE2, SSE3, SSE4.1, SSE4.2, AVX, AVX2, ...

Высоко-точный таймер (QueryPerformanceCounter). Возвращает `u64` (ticks).

### `CPU::GetCLK()`

RDTSC (Raw Time Stamp Counter). Возвращает `u64` (такты CPU).

**Инициализация**: `_initialize_cpu()` — вызывается в `xrCore::_initialize`. Заполняет `CPU::ID`, вычисляет `clk_per_second` и т.д.

## SIMD-диспетчеризация

Многие математические функции имеют **несколько версий** (SSE, SSSE3, AVX), выбираемых по `CPU::ID` в runtime. Механизм — `xrCPU_Pipe` (см. [Архитектура: Карта модулей](../../architecture/module-map.md)).

> В `xrCore` — только **интерфейсы** (`FPU`, `CPU::QPC`, `_processor_info`). Конкретные SIMD-версии — в `xrCPU_Pipe`.

**На пальцах**: возьмём, например, `dot` (скалярное произведение). Для него существует 3 реализации — под SSE2, под AVX и «обычная» (скалярная). При старте движка функция `_initialize_cpu()` (см. раздел «CPU» ниже) читает CPUID и кладёт в `CPU::ID` флаги возможностей. Дальше «диспетчер» (`xrCPU_Pipe`) выбирает **одну** быструю версию, совместимую с вашим CPU, и подменяет на неё адрес функции. После этого **все** вызовы `v.dot(w)` в коде уходят в ту быструю версию — вам не нужно ни о чём думать. Единственное, о чём стоит помнить: если вы пишете **новый** SIMD-код (новый fast-path), его нужно зарегистрировать в `xrCPU_Pipe`, а не разбрасывать `__m128` по `xrCore`.

## Частые ошибки новичков

- **`mul` vs `dot`**: `v.mul(w)` — **покомпонентное** умножение (`x*w.x, y*w.y, z*w.z`), `v.dot(w)` — **скалярное** (одна Zahl: `x*w.x + y*w.y + z*w.z`). Путать их — классика; `dot` возвращает `float`, `mul` — `Fvector`.
- **`lerp` заменяет, `add` добавляет**: `v.lerp(a, b, t)` → `v = a+(b-a)*t` (текущее значение стирается), `v.add(a)` → `v = v+a`. Для «сдвига» — `add`, для «перехода между двумя точками» — `lerp`.
- **Трансляция в `m41..m43`, а не `m14..m34`**: см. блок «Почему трансляция в m41, m42, m43» выше. Матрица сдвига на 5 по X — это `M._41 = 5.f`.
- **Кватернион без `normalize`**: после ручного `lerp` (не `slerp`) кватернион перестает быть unit, и `q * P * q'` даёт искажение. Если не уверены — вызовите `q.normalize()`.
- **Положительный угол = по часовой**: в этом движке (DirectX convention) «+90°» вращает **по часовой**, а не против, как в стандартной математике. Если поворот «в обратную сторону» — смените знак угла, а не формулу.
