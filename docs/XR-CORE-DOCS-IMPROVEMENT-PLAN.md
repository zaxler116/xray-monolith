# План улучшения документации xrCore — 10 этапов

> Рабочий документ-план. Целевая аудитория — разработчик, который впервые
> встречается с кодом движка и хочет понять, *что к чему*, а не просто
> просмотреть список функций. После каждого этапа документация xrCore
> (`docs/docs/modules/xr-core/`) должна быть самодостаточнее и понятнее.
>
> **Принципы всех 10 этапов:**
>
> - **Простой язык**: каждое абстрактное понятие объясняется через
>   «что это даёт программисту, который пишет код движка». Метафоры
>   допустимы, но только если они не вводят в заблуждение.
> - **Примеры с реальными именами** из этого кодабаза (`settings.ltx`,
>   `gamedata/levels/...`, `FS.r_open("levels/test.ltx")`), а не абстрактные
>   «какой-то файл».
> - **Поясняющие блоки**: для каждого нового термина — короткий абзац
>   «что это и зачем» до того, как показывать сигнатуру.
> - **Не удалять**: все существующие таблицы API, mermaid-диаграммы и
>   разделы «Ограничения / дебаг» сохраняются. Улучшение — только
>   добавление пояснений, контекста и примеров.
> - **Проверка**: после каждого этапа — `mkdocs build --strict`.

  платформах), а `Fvector`/`Fmatrix` — потому что движку нужны

  (а не `m14,m24,m34`), и **пример**: «если вы создаёте матрицу

## Этап 3. Память: почему один аллокатор и как это работает

**Файл**: `memory.md`

**Что сделать:**

- Вводный блок **«Зачему нужен единый аллокатор»**: объяснение, что
  если каждый модуль использует свой `malloc`, невозможно отследить
  утечки, посчитать потребление, и невозможно гарантировать, что память
  будет выделена из правильного пула. Единый `Memory.mem_alloc` — это
  «единая касса» для всех.
- Раздел **«Как работает `mem_alloc`»**: пошагово, что происходит при
  вызове (проверка пула → если не пул, Windows heap → учёт в отладке).
  С примером: `xr_alloc<Fvector>(100)` → выделение 1200 байт с именем
  `"Fvector"` (при `DEBUG_MEMORY_NAME`).
- Для `MEMPOOL` — **конкретный пример**: «у нас есть 64 пула; пул №3
  настроен на элементы 64 байта, сектор 64 КБ. Если вы выделяете 64
  байта — идёт из пула №3, не из общего heap. Это быстро, потому что
  нет обращения в Windows». Таблица: какие пулы для каких размеров.
- Раздел **«Отладочные режимы»**: таблица `DEBUG_MEMORY_NAME` /
  `DEBUG_MEMORY_MANAGER` / `memory_monitor` с объяснением *когда и зачем*
  включать каждый (не просто «включает имена», а «включите, если
  подозреваете утечку в конкретном модуле»).
- Пример **«Как найти утечку»**: пошаговый сценарий — включить
  `DEBUG_MEMORY_NAME`, запустить игру, `Memory.mem_statistic("dump.txt")`,
  посмотреть, что не освобождено.
- **Важно**: добавить предупреждение, что `xr_free<T*&>(P)` принимает
  *ссылку* — показать пример правильного и неправильного вызова.

**Критерий**: читатель может объяснить, почему `new Fvector()` идёт через
`Memory`, и знает, какой отладочный режим включить при подозрении на утечку.

## Этап 4. Строки: `shared_str` — глубокое объяснение интернирования

**Файл**: `strings.md`

**Что сделать:**

- **Главный блок**: «`shared_str` vs `xr_string` — когда что использовать».
  Таблица: критерий (частота сравнения, размер, временность) → тип.
  Примеры из движка: имя файла в `FS.r_open("levels/test.ltx")` —
  `shared_str` (сравнение по указателю, CRC), буфер для форматирования
  лог-сообщения — `xr_string`.
- **Интернирование на пальцах**: пошагово, с конкретной строкой
  `"hello"`, что происходит: CRC вычисляется → ищется в контейнере →
  не найдено → выделяется → `dwReference=1`. Второй `shared_str s2 =
  "hello"` → CRC совпадает → тот же указатель → `dwReference=2`.
  Уничтожение → `dwReference--` → при 0 — освобождение.
- **Почему CRC, а не хеш-таблица с полным сравнением**: объяснение,
  что CRC — быстрый предфильтр, коллизии разрешены (разные строки с
  одним CRC — разные `str_value`, но при сравнении по содержимому
  различаются).
- Раздел **«Что будет, если использовать `shared_str` неправильно»**:
  3–4 конкретных сценария (временная строка → лишний CRC + аллок;
  очень длинные строки → память; `printf` с обрезкой 4096).
- Пример **«Как читать лог-сообщение с `shared_str`»**: показать,
  что `Msg("file: %s", *ss)` работает, и почему `*ss` — это `const char*`.
- В разделе `smem_container` — короткое объяснение: «это то же самое,
  но для байтовых буферов, не для строк; используется, например,
  для кэширования CRC-подписей файлов».

**Критерий**: читатель может объяснить, почему `ss1 == ss2` (одинаковое
содержимое) — это сравнение по указателю, и знает, в каких случаях
нужен `xr_string` вместо `shared_str`.

## Этап 5. Логирование: как работает `Msg` и когда что использовать

**Файл**: `logging.md`

**Что сделать:**

- Вводный блок **«Два канала вывода»**: объяснение, что `Msg` пишет
  одновременно в файл (или файлы) и в callback (консоль / удалённый
  клиент). Почему это удобно: один вызов — и лог в файле, и в консоли.
- **Разница `Msg` vs `Log`** — ясная таблица: `Msg` форматирует
  (как `printf`), `Log` не форматирует `msg`, только `dop`. Пример:
  `Msg("frame %u, pos %f %f %f", frame, VPUSH(pos))` vs
  `Log("frame", frame)`.
- Раздел **«Когда лог ещё не создан»**: объяснение, что до `InitLog()`
  `Msg` пишет только в callback (если установлен). Почему это важно:
  если вы пишете `Msg` в конструкторе — проверьте, что `InitLog` уже
  вызван.
- Пример **«Типичные паттерны логирования»**: 3–4 реальных примера
  из движка (старте, при ошибке, при отладке), с пояснением, *почему*
  именно так.
- Раздел **«Как добавить свой лог-файл»**: пошагово, как добавить
  ещё один файл в `LogFile` (для отладки конкретного модуля).
- **Важно**: блок «Почему `Msg` — `__cdecl`, а не `__stdcall`» —
  коротко, но понятно (varargs → нужен cleanup у вызывающего).

**Критерий**: читатель знает, какой вызов использовать для
форматированного вывода, и понимает, почему `Msg` до `InitLog` может
ничего не писать в файл.

## Этап 6. Файловая система: chunking, квантование, `IReader`/`IWriter`

**Файл**: `filesystem.md`

**Что сделать:**

- **Главный блок**: «`IWriter`/`IReader` — это *язык* бинарных форматов
  движка». Объяснение, что любой LTX-файл, сохранение, сетевой пакет —
  всё это последовательность `w_u32`/`r_u32`/`w_fvector3`/`r_fvector3`.
- **Chunking на пальцах**: пошагово, с примером. «Вы пишете LTX-файл
  объекта. Вызываете `open_chunk(123)` → в файл пишутся 8 байт
  заголовка (type=123, size=0). Потом пишете данные: `w_u32`, `w_float`
  и т.д. Вызываете `close_chunk()` → движок переписывает size в
  заголовок. При чтении: `find_chunk(123)` → сканирует файл, находит
  chunk, возвращает размер. `open_chunk(123)` → ставит позицию на
  данные. `r_u32`/`r_float` — читает.»
- **Квантование — зачем и как**: объяснение, что `w_float_q16(a, 0, 1)`
  кодирует float в 16 бит (вместо 32), теряя точность, но экономя
  память. Пример: угол 0–360° → `w_angle16` → 2 байта. Показать
  формулу и обратную, с числовым примером (a=45°, min=0, max=360 →
  q16 = 45/360*65535 ≈ 8191).
- **Разница `IReader` (in-memory) vs `CStreamReader` (windowed)**:
  таблица: когда что использовать. `IReader` — для малых файлов
  (<1 МБ), загруженных в память. `CStreamReader` — для больших
  (gamedata-архивы), читает «окном» 1–4 МБ.
- **`w_string` vs `w_stringZ`**: ясное объяснение: `w_string` добавляет
  CRLF (13,10) — для INI-подобных форматов; `w_stringZ` добавляет `\0`
  — для бинарных форматов. **Не перепутать** — это частая ошибка.
- Пример **«Как сериализовать свой объект»**: пошагово, с кодом:
  `void CMyObject::save(IWriter& W) { W.w_u32(m_id); W.w_fvector3(m_pos); W.w_stringZ(m_name); }`
  и обратное.

**Критерий**: читатель может самостоятельно написать `save`/`load`
для своего класса, понимая, что такое chunk, и почему `w_stringZ`
а не `w_string`.

## Этап 7. INI/LTX: DLTX — как работает система override

**Файл**: `inifile.md`

**Что сделать:**

- **Главный блок**: «LTX — это не просто INI». Объяснение, что LTX —
  это текстовый формат с секциями, но с *системой override* (DLTX),
  которая позволяет mod-файлам переопределять base-файлы. Это ключевая
  особенность, без которой невозможно понять, почему `settings.ltx`
  может быть переопределён.
- **DLTX на пальцах**: сценарий. «У нас есть `base/settings.ltx`
  (секция `[renderer]`, `r4 = true`). И `mod/settings.ltx` (секция
  `[renderer]`, `r4 = false`). При загрузке движок видит, что mod-файл
  имеет меньший depth → его значение побеждает. Итог: `r4 = false`».
  Таблица: depth, insertionIndex, кто побеждает.
- **Include в LTX**: пример. `[section:include "other.ltx"]` — что
  происходит: файл `other.ltx` читается рекурсивно, его секции
  добавляются. Если есть конфликт — решает depth.
- **Кэш**: объяснение, почему кэш нужен (повторное чтение того же
  файла — редкость, но если файл изменён в редакторе — нужен
  `InvalidateCache`).
- **`r_string` vs `r_string_wb`**: ясная таблица с примерами:
  `key = "value"` → `r_string` = `"value"` (с кавычками),
  `r_string_wb` = `value` (без кавычков). Когда что использовать.
- Пример **«Как прочитать конфиг уровня»**: пошагово, с реальным
  именем файла (`levels/test.ltx`), что делать: `CInifile::Create`,
  `r_section("level")`, `line_exist`, `r_string`.

**Критерий**: читатель понимает, почему mod-файл может переопределить
base-файл, и знает, как прочитать конкретную секцию из LTX-файла.

## Этап 8. Сжатие: LZO vs PPMd — когда что использовать

**Файл**: `compression.md`

**Что сделать:**

- **Главный блок**: «Два алгоритма, две задачи». LZO — быстрый,
  для данных, которые читаются каждый кадр (LTX-чунки, сохранения,
  сеть). PPMd — медленный, но сжимает сильнее, для данных, которые
  читаются редко (gamedata-архивы при загрузке). Таблица: скорость,
  степень сжатия, когда использовать.
- **`rtc_csize` — почему это важно**: объяснение, что LZO *может*
  увеличить данные (если они не сжимаются). `rtc_csize(in)` возвращает
  *максимальный* размер — вы должны выделить буфер такого размера.
  Пример: `rtc_compress(dst, rtc_csize(src_len), src, src_len)`.
- **PPMd trained model**: объяснение, что это предобученная модель,
  которая «знает», какие паттерны часты в gamedata. При сжатии с
  trained model — сжимает сильнее, чем без. При декомпрессии — та же
  модель. Где хранится: глобальная `trained_model`, инициализируется
  в `xrCore::_initialize`.
- **Multi-thread PPMd**: объяснение, что `ppmd_compress_mt` с
  `yield_callback` — это кооперативная многопоточность: функция
  периодически вызывает callback, чтобы отдать управление другому
  потоку. Это *не* preemptive — вы должны сами вызывать yield.
- Пример **«Как сжать данные при записи в файл»**: пошагово, с кодом:
  `W.w_compressed(data, size)` → внутри: `rtc_compress` → chunk с
  `CFS_CompressMark` → при чтении `find_chunk` видит mark →
  `r_chunk` распаковывает.
- **LZHUF**: короткое объяснение, что это старый алгоритм, оставшийся
  от X-Ray 1.5, не использовать для новых данных.

**Критерий**: читатель знает, какой алгоритм использовать для
конкретной задачи (LTX-чунки → LZO, gamedata → PPMd), и понимает,
почему `rtc_csize` обязателен.

## Этап 9. Локализатор: виртуальная ФС — как `FS.r_open` находит файл

**Файл**: `locator.md`

**Что сделать:**

- **Главный блок**: «`FS.r_open("levels/test.ltx")` — что происходит
  внутри». Пошагово: 1) `exist` → ищет в `m_files` (set по имени,
  low-case). 2) Если `vfs == 0xffffffff` → стандартный файл →
  `CFileStreamReader`. 3) Иначе → из архива → `CStreamReader`
  (memory-mapped, windowed). 4) Если `flCacheFiles` → из кэша.
- **Архивы `.ltx`**: объяснение, что `.ltx`-архив — это файл, внутри
  которого в начале — header (LTX-формат, список файлов с offset/size),
  а после — сами файлы. `CInifile* header` в `archive` — это этот
  header. `Register` — добавляет файл в `m_files`.
- **Приоритет файлов**: ясная таблица: папки > архивы (в порядке
  сканирования). Почему: если файл есть и в папке, и в архиве —
  берётся из папки (можно модифицировать).
- **Auth**: короткое объяснение, что `auth_generate` — это CRC всех
  важных файлов → `m_auth_code`. Это антипират, не для отладки.
  Если `m_auth_code` не совпадает — игра не запустится.
- **Rescan**: объяснение, что это только для редактора (`_EDITOR`).
  В игре — фиксированный набор файлов.
- Пример **«Как добавить новый файл в gamedata»**: пошагово:
  положить в папку → `FS.r_open` найдёт (папка > архив). Или
  в архив → нужно пересобрать архив.
- **`w_open`**: объяснение, что запись идёт *только* в папки
  (не в архивы), и `can_write_to_folder` проверяет, что папка
  доступна.

**Критерий**: читатель может объяснить, почему файл из папки
переопределяет файл из архива, и знает, что делать, если `FS.r_open`
вернул `nullptr`.

- **Таймеры — иерархия на пальцах**: дерево: `CTimerBase` (базовый,
  QPC) → `CTimer` (с time_factor) → `CTimer_paused_ex` (пауза) →
  `CTimer_paused` (авторегистрация в `pauseMngr`). Когда что
  использовать: `CTimer` — для профайлинга (можно ускорить время),
  `CTimer_paused` — для игровых таймеров (пауза при паузе игры).
- **`pauseMngr`**: объяснение, что это глобальный менеджер: все
  `CTimer_paused` автоматически регистрируются. `Pause(true)` →
  все таймеры останавливаются. `Pause(false)` → все возобновляются.
- **Синхронизация — таблица выбора**: `xrCriticalSection` (Windows
  CRITICAL_SECTION, не рекурсивный) vs `Lock` (std::mutex,
  рекурсивный) vs `xrSRWLock` (reader-writer). Когда что:
  `xrCriticalSection` — для коротких секций (быстрый), `Lock` —
  если нужен рекурсивный (вложенный Enter), `xrSRWLock` — если
  много читателей, один писатель.
- **RAII-guards**: объяснение, что `ScopeLock`/`xrCriticalSectionGuard`
  — это «замок, который сам откроется при выходе из блока». Пример:
  `xrCriticalSectionGuard guard(&cs); // дальше код под замком`.
- **`Debug.fail` vs `soft_fail`**: ясная таблица: `fail` — падает
  (crash, stack trace), `soft_fail` — только лог. `R_ASSERT` → `fail`
  (в debug), `VERIFY` → `fail` (debug) или `soft_fail` (release,
  при `USE_VERIFY_IN_RELEASE`).
- **`NET_Packet`**: объяснение, что это бинарный пакет для сети,
  16 КБ лимит. `w_*`/`r_*` — аналогично `IWriter`/`IReader`, но
  с `INI_W` (дублирование в INI-файл для отладки). Пример:
  `packet.w_begin(123); packet.w_u32(id); packet.w_fvector3(pos);`
- **`CLASS_ID`**: объяснение, что это 8-байтный ID (8 × u8),
  `MK_CLSID(a,b,c,d,e,f,g,h)` — конструктор, `CLSID2TEXT` — текстовое
  представление (для отладки). Пример из движка.
- **Профилирование**: короткое объяснение, что `XRCORE_PROFILER`
  (NONE/OPTICK) — это интеграция с Optick (внешний профайлер).
  `PROF_FRAME`, `PROF_EVENT` — макросы для разметки.

**Критерий**: читатель знает, какой таймер использовать для
конкретной задачи, какой lock выбрать, и понимает, что
`R_ASSERT` в debug приведёт к падению.
